# Архитектура пилота

## Что именно автоматизируем

Сотрудник брокерского бэк-офиса получает исключение по количеству исполненных акций. Ему нужно решить, дождаться выгрузки, запросить запись или передать случай на исправление. Карточка уже содержит срез по сделке. Агент читает пояснения к корректировкам и применимый регламент и предлагает проверяемое действие. В публичном демо проверяем сам рабочий процесс на синтетике.

| Контур | Реализация | Результат |
| --- | --- | --- |
| Публичное демо | HTML, CSS и JavaScript на GitHub Pages | Сверка в браузере, четыре синтетических случая, заготовленные подсказки, повторная сверка и локальная история |
| Закрытый пилот | Один Python-сервис на FastAPI, PostgreSQL, одна модель с проверяемым JSON-выходом | Импорт обезличенных данных, история сверки, ответы модели и решения сотрудников |

## Поток данных

1. Адаптер T-Invest MCP читает операции и состояния заявок с разрешённых счетов. Второй вход принимает согласованный файл клиринга и комментарии к корректировкам. Ответы сохраняются в привязке к источнику, версии и времени доступности. Проверяем фактические схемы на обезличенных записях до пилота.
2. Сверка фиксирует момент разбора `as_of`, исключает более поздние записи и сравнивает количество акций по каждому источнику. Использует только подтверждённые идентификаторы. Если нескольких кандидатов нельзя различить, возвращает `unresolved` и сохраняет кандидатов для сотрудника.
3. Для неоднозначного случая сервис выбирает применимые пункты регламента по типу расхождения и периоду действия. Одного запроса к PostgreSQL достаточно для начального набора правил. Модель получает срез и выбранные пункты.
4. Сервис проверяет ответ модели по схеме и принимает ссылки только из среза. При тайм-ауте, ошибке схемы или недопустимой ссылке карточка остаётся доступной со сверкой. Решение сотрудника сохраняется отдельно с временем и версией среза.

## Где именно нужен ИИ

У обычной сверки уже есть точный результат — 100 / 100 / 90. Следующий вопрос сотрудника — что означает комментарий и достаточно ли его, чтобы закрыть случай. Постторговые платформы уже поддерживают обнаружение и обработку исключений. Наша гипотеза касается времени на разбор свободного текста и выбор проверки в неоднозначных случаях. [DTCC CTM](https://www.dtcc.com/products-and-services/trade-processing-solutions/ctm).

1. Сервис собирает фиксированный срез. Он ищет комментарии по ID связанных записей и выбирает действующие пункты регламента по типу исключения и времени. Срез содержит только доступные на тот момент источники.
2. Модель читает исходный текст комментария вместе со сверкой и регламентом. Например, формулировка «корректировка ожидается» позволяет предложить версию об исправлении, но оставляет открытым вопрос о фактическом поступлении исправленной строки.
3. В ответе разделяем факты, возможную причину, недостающее подтверждение и следующее действие. Факты из сверки формируются кодом. Для версии и действия модель указывает ID записей и пунктов регламента. Если оснований мало или они противоречат друг другу, результат — «недостаточно данных» с указанием конкретной проверки.
4. Сервер проверяет допустимые ссылки и коды действий. Сотрудник проверяет содержание и сохраняет собственное решение. При повторной выгрузке статус пересчитывается правилами. Проверка существования ссылки и проверка обоснованности вывода — отдельные проверки. [NIST AI 600-1](https://doi.org/10.6028/NIST.AI.600-1).

В публичном демо поиск и генерация показаны с короткой задержкой, а результаты заранее подготовлены на синтетике. Эксперимент с сотрудниками отдельно проверяет, сокращает ли такой разбор время по сравнению с той же карточкой без модели.

## Контракты

- Входной ключ записи — источник, идентификатор строки и версия выгрузки. Случай хранит идентификатор, инструмент и время разбора. Количество для пилотного сценария — целое число акций, время — UTC.
- Три состояния сверки — `matched`, `mismatch`, `unresolved`. Если данных недостаточно для сопоставления, сначала выставляется `unresolved`. Иначе расхождение в количестве даёт `mismatch`, равенство — `matched`.
- Ответ агента — причина или явное указание, что её пока нельзя установить, список ссылок, код следующего действия и пояснение. Коды для пилота — `wait_for_export`, `request_record`, `escalate`.
- Минимальные серверные операции — импорт пакета, получение карточки по ID, запрос подсказки по версии среза и запись решения. Повторный импорт одного пакета не размножает строки. Решение привязывается к конкретному срезу, чтобы последующий импорт не изменил основания задним числом.
- Таблицы PostgreSQL — `cases`, `source_records`, `policy_rules`, `analysis_runs`, `decisions`. Поля, нужные для сверки и поиска регламента, хранятся отдельно. Исходный обезличенный payload можно хранить в JSONB для воспроизведения.

## Проверки перед пилотом

| Проверка | Условие приёмки |
| --- | --- |
| Публичный показ | Четыре сценария открываются на GitHub Pages. Сверка проверяет все три источника, ссылки ведут к демо-записям, после следующей выгрузки статус пересчитывается, а решения и предыдущий срез остаются в истории. |
| Реальные источники | Независимый эксперт подтвердил связи на серии случаев. Измерены покрытие и доля ошибок сопоставления. Условия допуска к пилоту заранее согласованы с брокером. |
| Ссылки и сбои | Ссылка открывает конкретную переданную запись или пункт регламента. При недоступности модели сверку можно завершить вручную. |
| Польза | На отдельной выборке сравниваем ту же карточку с подсказкой и без. Согласуем границу для ошибок и размер выборки до основного эксперимента. Целевое сокращение медианного времени составляет 20%. |

Порядок работ — публичное демо и проверка реальных источников параллельно, затем закрытый пилот. Публичная страница не получает токены, данные брокера или запросы к модели.
